# Split-repository portability pilot

- Status: completed 2026-08-24
- Scope: sanitized project-home learning from one read-only structural pilot
- Exact evidence: retained in the authorised ignored private lane

## Question

Can the project-owned adoption model route a private control workspace and a separate
public-capable implementation repository without copying private truth, creating shadow
Canon, or confusing later Git, provider, publication, deployment, and release gates?

## Observed result

The inspected project used two sibling Git roots:

- a control workspace owned operating direction, private evidence, human decisions,
  and release approval;
- a website repository owned runtime, UI, package, build, test, and public-candidate
  truth.

A full ignored-local profile at the control layer kept its exact cross-root routing
record outside the website's tracked lane. The website's tracked orientation and
release gate were sufficient for its observed single-purpose implementation role; a
second full profile would have added symmetry, not clarity.

The sibling structure supported the existing
[proportional adoption strategy](../adoption-strategy.md). It avoided nested-Git
ambiguity and kept implementation truth in the implementation repository.

## Material friction

Ignored local routing can become stale after a later, separately approved lifecycle
action. In this pilot, the routing record still described a pre-baseline Git state even
though live Git had moved on.

That did not make the two-root model unsafe: live Git remained the observed source for
repository state. It did show that later closeout must do one of two things:

1. reconcile target-owned ignored continuity under explicit target authority; or
2. mark the local record stale and bind every current claim to live identity evidence.

A project home may retain this generalized learning. It must not repair, copy, or
silently supersede the target's private routing and lifecycle truth.

## Coverage limits

This pilot did not run either target's validators, tests, builds, runtime, UI, provider,
publication, deployment, or release checks. It did not assess business claims, private
evidence, customer material, credentials, or current provider visibility.

The result supports structural routing only. It is not proof of target correctness,
publication readiness, deployment health, product demand, or plugin compliance.

## Decision state

- Existing project-owned proportional adoption remains supported.
- No target correction is authorised by this summary.
- No plugin implementation change is accepted.
- A later decision may close with documentation-only learning, authorise a target-owned
  continuity correction, propose a small implementation-owned reconciliation aid, or
  request another pilot.

Runtime/UI impact: none.

Migration or restart: none.

Publication, deployment, and release impact: none.
