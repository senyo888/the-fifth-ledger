# Product direction and positioning

## Working objective

The Fifth Ledger should help maintainers and coding agents keep consequential project
work coherent across five views of truth:

1. authority;
2. canon;
3. evidence;
4. surfaces; and
5. lifecycle.

Its practical value is disciplined routing and decision quality: identify who may act,
locate the source that owns the topic, bind claims to current evidence, keep outward
surfaces truthful, and stop lifecycle states from collapsing into one another.

## Working positioning

The Fifth Ledger is a governance workflow layer for agentic project work. It is not an
access-control product, a security scanner, a compliance certification, a runtime
orchestrator, or an authority system.

The current product hypothesis is that maintainers need a portable, local-first way to
make agent work reviewable without importing a large process framework. That hypothesis
requires bounded pilots and current market research before any stronger demand,
differentiation, or adoption claim.

## Intended users

- maintainers using coding agents across repositories and lifecycle stages;
- teams with separate public, private, evidence, and implementation lanes;
- projects where documentation, implementation, release, and external state can drift;
- reviewers who need clear blockers, disagreements, and decision ownership.

## Product principles

- Project truth remains project-owned.
- Governance scales with impact and uncertainty.
- Routing is not precedence.
- Evidence is identity- and time-bound.
- Unknown and unavailable states remain visible.
- Proposal, implementation, validation, publication, deployment, and release remain
  distinct.
- Independent review is claimed only when the context is genuinely separate.
- The smallest useful artifact is preferred over ceremonial repetition.

## Non-goals

- granting filesystem, repository, provider, or organizational permissions;
- copying adopter policy into a global canon;
- autonomous approval, publication, deployment, or release;
- collecting telemetry or private adopter evidence by default;
- replacing CI, branch protection, security controls, legal review, or human ownership;
- duplicating the plugin implementation in this project home.

## Questions requiring evidence

- Which project types gain enough value to justify adoption?
- What is the smallest profile and workflow that improves decisions without adding
  friction?
- Which controls belong in procedural skills and which require external enforcement?
- What public evidence can demonstrate value without exposing adopter truth?
- Should the project home and implementation repository eventually share a remote
  organization, remain separate, or use another arrangement?

These are research and decision questions, not implied roadmap commitments.
